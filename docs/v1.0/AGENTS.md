# 拾史产品迭代规则

本目录是拾史的独立产品设计仓库，不操作上级目录的其他项目。当前为 v1.0 设计基线，正式应用尚未实现。先读取 VERSION、版本管理.md、CHANGELOG.md、拾史桌面端V1_PRD.md、技术架构/技术架构说明.md 和需求追踪.json。

1. 产品行为以当前 PRD 为需求源，架构、原型、字段、任务和验收需映射到 F01–F42 或后续新增编号。需求编号不可被复用于不同需求。
2. 确认新需求对哪些页面、模块、数据、费用和历史项目有影响。更新受影响文件，不得只改原型或只改代码。无影响的项也在变更记录中说明。
3. VERSION 是版本号唯一入口；发布时所有派生文档与原型标签必须一致。v1.0 已冻结文件不可静默改写，新增版本重新生成并建立新标签与快照。
4. Word 是 PRD Markdown 的派生文件；先改 Markdown，再用 tools/build_prd.py 生成 Word，完成渲染与逐页检查。原型图必须从当前原型重新导出。
5. 需求追踪.json 保存需求文本摘要、页面、模块和验收映射。同步检查不仅要覆盖编号，也要检测文本和文件变化。哈希不能替代人工语义检查，变更日志必须记录实际做过的评审。
6. 发布前运行 tools/check_sync.py；通过后才可生成不可覆盖的版本快照。记录验证证据，提交 Git 并打新版本标签，禁止重写既有版本标签。
7. 当前交付只包含设计与同步工具。不要把原型状态当成真实 AI、任务或费用能力。产品运行任务需单独锁定偏好、Skill、schema、模型配置和时间线版本。
8. 不提交密钥、用户上传书页、运行数据库与私有媒体。服务商接口与付费调用需要接入验证和实际预算授权；设计稿预算不构成付费授权。
